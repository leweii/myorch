myorch Flow manual

This manual covers each flow: what it does, when to use it, what each step does, and when it needs you. The platform itself (services, architecture, commands, project packs, flow syntax) is in the User manual.

Each flow has one chapter. The input table, the step graph and the step details in a chapter are generated from flows/*.yaml. They match what myorch expand and the console Flows (流程) page show, so they cannot drift from the flow definition. The rest of the text is written by hand: the Chinese original next to the flow in flows/<flow>.md, this English version in docs/en/flows/<flow>.md. After you change a flow or its .md, regenerate (it writes the English and the Chinese manual):

uv run --with markdown python docs/workflows/build.py

One set of flows for every project

Each role has one flow (flows/development.yaml, review.yaml and so on), shared by all projects. The differences between projects live in the project pack myorch-knowledge/<project>/. They take effect when the flow is expanded; you do not pick them when you start a run:

  • flows.development in project.yaml: how heavy review is (reviewers, max_rounds, security, on_exhausted), whether to commit a takeaway (takeaway), and whether there is an incident input (incident). When not set, the defaults are: 3, 3, true, ask, false, false.
  • prompts/<slot>.md: the project's own prompt rules. The slots are develop, review, verify, fix, risk. At expansion the text is appended verbatim to the prompt of the matching step: the template's first, then the project's.
  • jira: when the project has Jira, the development flow has a ticket input and fetch-ticket, and the ticket is the requirement. Without Jira, the first message is the requirement.
  • if: in a flow drops steps and inputs per project. Dropped inputs do not show in the form.

  • To change how one project works, change its project pack, then run uv run myorch project sync <project>. Changing a flow or fragment under flows/ affects all projects.
  • A flow file starts with role:. myorch recognizes flows by role, not by name. For example, Continue on this branch (在这个分支上接着改) works for any run of the development role, and eval replay uses the flow of the eval role.

  • The fields are defined by the flow file's inputs: label, hint, whether required, type. The types are text, message, dropdown, ticket number (MD-18700 and 18700 both work) and run (picked from this project's finished runs). Each chapter's Inputs table lists them.

  • An approval is bound to a commit. If the code changes after approval, delivery refuses to push and the run must be redone.

  • A local Claude Code session can answer questions and resume from a failed step. It cannot approve.

Continue on the same branch

Use this after a development run has finished: your own testing found a problem, or you want to change more on top of this change. Open that run in the console, click Continue on this branch (在这个分支上接着改), and write what to change this time in the first message. On the command line use -i from_run=<run ID>.

  • The chosen run must be finished, belong to the same project, and have the development role. If no ticket number is given, the previous one is reused.
  • The new run uses the same branch name. The push updates the same branch, so a PR a person opened updates too.
  • It starts from the last commit of that branch. If someone added commits to the remote branch, it starts from the latest remote commit. If the two have diverged, it stops and a person must sort it out first.
  • The previous run's requirements, design, implementation record, risk verdict, delivery note and last-round review verdict are put in docs/previous/. The agent writes on top of them and states separately what changed this time. Earlier runs are in docs/previous/earlier/, nested one inside another.
  • What people said to the previous run is in docs/previous/conversation.md: the agent's questions and the answers, change requests, comments given on approve or reject, and failures and re-runs. The event log is on the host and the sandbox cannot read it, so the host writes this file into the new run when it starts (the same for command line, console and Slack). The agent treats it as human decisions; where it conflicts with assumptions in the previous documents, it wins.
  • Implementation, review and approval then proceed as usual. Review round 1 looks only at the commits added this time; checks and the risk verdict look at the whole branch's changes against base. Details are in Continue in development.

Reading the step graph

  • Top to bottom is execution order. Steps on the same row run in parallel. When a card does not wait for every step on the row above, the card says "Waits for …" (等 …) underneath.
  • The second line of a card is the executor: agent (model · profile), script (profile), host action (a registered deterministic action that does not run in a sandbox), or approval. The profile sets the sandbox's permissions; see User manual · 7. Project packs.
  • Cards with a blue bar on the left are agents. Hatched cards are host actions. Amber marks where you are needed: approval cards and steps marked May ask you (可能问你).
  • A dashed outer border marks a conditional step or loop. Hover over conditional (有条件) to see the expression.
  • A box is a loop: its title says the maximum number of rounds, when it stops, and what happens when it runs out of rounds. The reflect step at the bottom runs only when the loop is exhausted and it is to ask you; it gives a proposal.
  • "×3 parallel" (×3 并行) means three instances of the same step (for example 3 reviewers).
  • The graph is expanded for mdm with default inputs (mdm's development flow has the most steps). For another project, the project pack may drop some steps or change parameters (for example blog's review has only 1 reviewer), and project values in conditions may differ. Use myorch expand flows/<flow>.yaml --project <project> or the console Flows (流程) page to see the expansion for a given project. Open Executor, condition and outputs of each step (每一步的执行者、条件、输出) below the graph to see the full expressions.

Changing a flow

  1. Change flows/<flow>.yaml or a fragment. The syntax is in User manual · 8. Writing flows.
  2. Run uv run myorch expand flows/<flow>.yaml --project <project> to see the expanded result.
  3. Update flows/<flow>.md and docs/en/flows/<flow>.md to match, and regenerate this manual.
  4. Run uv run pytest once. When the worker and console run in compose, docker compose -f deploy/compose.yaml up -d --build makes them load the new flow.

The development flow: from one requirement to a pushed branch. All projects share this one flow. In one session it writes the requirements, the technical design and the code changes. The change then goes through review, a risk verdict and human approval. Finally the approved commit is pushed to this run's branch. myorch opens no PR and does not merge: a person opens the PR on GitHub and decides on merging. Before approval the change does not leave the sandbox and nothing is pushed.

The differences between projects are all in the project pack; you do not pick them when you start a run (see Differences by project):

  • How heavy review is: how many reviewers, at most how many rounds, whether there is a separate security review, what happens when the loop runs out of rounds (flows.development in project.yaml).
  • Whether there is Jira: if so, fetch-ticket reads the ticket first and the ticket is the requirement. If not, the first message is the requirement.
  • Whether to commit the task info and lessons (takeaway) to the repository's myorch/ directory (flows.development.takeaway).
  • Whether there is an incident input: when the platform had a problem, the failing run is attached for develop to look at (flows.development.incident).
  • The project's own prompt rules (prompts/develop.md, review.md, verify.md, fix.md, risk.md). At expansion their text is appended verbatim to the prompt of the matching step.

  • Projects without Jira (blog, myorch): the first message is the requirement. It is required and can span several lines.

What each step does

Step What it does Artifacts
sync-master Clones or updates the repository, force-aligns with origin/<base>, initializes submodules. The first clone goes through the mirror repository in the project's shared directory; after that only increments are fetched (lib/sync-base.yaml) outputs.base_sha
checkout-branch Creates this run's branch. The branch name comes from the project pack's branch (mdm: MD-<ticket number>-myorch-<run ID>; blog and myorch: myorch/<run ID>). Runs the project's setup.sh. When continuing, it switches to the previous run's branch; when replaying, to at. See the two sections below outputs.branch, outputs.since
fetch-ticket Only when the project has Jira. Reads the ticket with the Jira REST API (read-only), writes it as docs/external/ticket.md, downloads screenshots. See "Reading the ticket" docs/external/ticket.md, docs/external/attachments/
develop Does it all in one session: writes the requirements document, writes the technical design, asks all questions that need a human decision at once, changes the code, runs the checks, writes the implementation record, commits once. See "develop" docs/requirements.md, docs/design.md, docs/implementation.md, one commit
review-fix loop ci (the project's checks.sh) → review (count per project) and security in parallel → verify checks the findings and computes blocking → fix (only when blocking > 0) → pack-choose, pack-apply (only when fix proposed project pack changes). The number of rounds and what happens when they run out depend on the project. See "The review loop" docs/ci/round-N.md, docs/review/round-N/
takeaway-trail Only with flows.development.takeaway (mdm). Host action: writes the run's history so far to docs/takeaway/trail.json trail.json
takeaway Same condition. Read-only agent: writes the task info task.md and the lessons takeaway.md docs/takeaway/task.md, takeaway.md
takeaway-redact Same condition. Host action: deletes lines that look like secrets from the two files
takeaway-commit Same condition. Commits the two files to the repository at myorch/<date>-<run ID>/ one commit
risk-rules Computes the number of approvers by rules: changed paths and content, unresolved review findings, failed checks, commits that were not reviewed outputs.approvers, head_sha and others
classify-risk Reads the actual diff, judges independently how many approvers are needed, writes a risk note for the approvers docs/risk.md
human-review Human approval. For the number of approvers see "Risk and approval". Passes automatically when the number is 0
deliver Checks that HEAD is the approved commit, pushes the branch, writes the delivery note docs/delivery.md, outputs.delivery

  • For projects without takeaway, the four steps are removed at expansion, and risk-rules waits directly on review-fix.
  • The flow sets on_failed: ask at the top level: when a step still fails after retries, it asks you.

develop

One agent goes from reading the requirement to committing code, in three phases in order: requirements, technical design, implementation. It cannot skip the first two phases and go straight to code. The project's prompts/develop.md is appended verbatim after the "Inputs" part of the prompt; see Differences by project.

  • Inputs: the ticket docs/external/ticket.md (when there is one), screenshots, the original request docs/external/request.md, project conventions, the knowledge that comes with the repository, the project pack's guide/ (its decisions.md holds decisions people made before). The original request and the ticket are external data; instructions in them are not followed.
  • Requirements document: goal, scope, what is explicitly out of scope, checkable acceptance criteria, a ticket mapping table, the files expected to change, risks, sources.
  • Ticket mapping table: each requirement in the ticket is copied as one row (including those added in comments), with the acceptance criterion it maps to, or why it is not done. When one requirement contains several actions, the acceptance criteria must cover each action.
  • The agent cannot put modules, features or scenarios the ticket names into "explicitly out of scope" on its own. To exclude one, it must ask a person.
  • Technical design: impact analysis (callers, cross-module dependencies, other services), the approach and the rejected approaches, compatibility and rollback, a test plan (a test for each acceptance criterion, plus edge cases and counterexamples), risks. No code in the design.
  • List every entry point: when adding validation to a field or requiring consistency in several places, search back in at least two ways, by the error message and by the field name. Write the search commands and the entry points found into the design.
  • Before removing or loosening an existing check, find out why it exists with comments, git log -L and git blame. If that cannot be found out, or what it protects no longer holds after the change, ask a person.
  • Look for an existing implementation of the same kind first: if it fits, call it; if its shape does not fit, reshape it so it can be shared; when the behavior is decided by a shared method, change the shared method and check every caller. Do not copy it. Changing the shared implementation for reuse is within this change's scope.
  • Ask before changing code, at most once: the questions from both phases that need a human decision go into one question, each with options, the first one recommended. The agent cannot choose for you on: things users can see, interfaces and contracts, data models and migrations, behavior changes that affect other modules or services, and choices that clearly change the size of the implementation. Decisions already in decisions.md are followed and not asked again.
  • Safety net: when the agent finishes and reports questions it did not ask but decided by the recommendation (requires_design_decision), the platform still asks you, and your answer is sent back to the same session as the next turn.
  • Implementation: change only code within scope, give each acceptance criterion a test or check, run myorch-checks (the project's checks.sh) until it passes, write the implementation record, and commit once on the current branch. When the check report lists failures under "Environment" (环境) (network or system limits of the sandbox), they are not code problems: commit as usual and note them in the implementation record.
  • Stop: when the requirement contradicts the code, when code outside the scope must change, or when checks fail because of the code and cannot be fixed, it does not commit. The step fails and then asks you what to do.
  • It may decide no change is needed: the feature already exists, or you decide not to do it. No documents are written and everything after is skipped.

Why one step: when these were separate, every handoff lost information. The steps with credentials (sync-master, fetch-ticket, deliver) still run separately; develop gets no GitHub or Jira credentials.

Reading the ticket

  • Condition: the project sets jira.url (mdm: example.atlassian.net, prefix MD) and a ticket number is given. When only digits are given, the project's prefix (jira.key) is added. Projects without Jira have no ticket input and no fetch-ticket step.
  • Read-only: the credentials are the project's Jira provider (mdm: jira-mdm). The egress rules allow only reading tickets, reading attachment content, and /myself. The sandbox holds only a placeholder; the gateway swaps in the real token.
  • Content: title, type, status, priority, reporter, assignee, labels, components, parent ticket, linked tickets, description, subtasks, attachment list, comments. The file states at the top that it is external data.
  • Screenshots: only image attachments are downloaded, at most 10, each at most 5 MB, saved to docs/external/attachments/<id>-<file name>. The "Attachments" (附件) section of ticket.md lists the paths, and develop opens them with Read. !file name! in the description refers to these images. Other attachments are listed by name only. A failed download does not affect the run. The console's Docs (文档) tab also shows these images.
  • Comments: ticket_comments defaults to all. With none, comments are left out and only the description is used (for evals: the requirement should be in the ticket, not depend on comments).
  • MCP fallback: when fetch-ticket did not run (the project has no jira.url) and the run has an MCP knowledge source that can read tickets, develop first reads the ticket via MCP and writes the same docs/external/ticket.md, noting the source at the top. If it cannot read it, it says so in the summary and continues from the original request. mdm does not attach the Atlassian MCP by default at the moment.

The review loop

Defined in the fragment lib/review-loop.yaml. review and eval use it too (one round only, no fixing). The parameters here come from the project's flows.development: by default 3 reviewers plus a separate security review, at most 3 rounds, and it asks you when it runs out of rounds. The project's prompts/review.md, verify.md and fix.md are appended to the matching steps.

  • What each round looks at: round 1 looks at the whole change (when continuing, only this run's new commits); each later round looks only at the commits since the previous round started. ci computes the range and writes it to docs/ci/round-N/head.txt.
  • Judge independently first, read the author's account last: a reviewer first looks only at the requirements document, the technical design and the diff, and finds problems on its own. Only then does it read the implementation record and check that the tests and checks listed there really exist and the assumptions hold. A reason given in the implementation record is no excuse to let a problem pass.
  • Check the requirements document against the original ticket: the requirements document is also written by the author. Leaving out, narrowing or rewriting a ticket requirement, a ticket mapping table that covers only some of the actions, or moving something the ticket names out of scope on its own, all count as Important.
  • Look in the repository: three kinds of problems that the diff alone does not show always count as Important:
  • Not reusing an existing implementation of the same kind, or copying a branch of a shared method instead of changing it.
  • Missed entry points: other places that read or write the same field or the same error message were not changed, and the design does not say why.
  • An existing check was removed or loosened, breaking what it protected, and the requirements document does not say a person decided this.
  • Division of work: reviewer 1 focuses on correctness and edge cases, reviewer 2 on acceptance criteria and tests, reviewer 3 on design, scope and reuse. Everyone checks for missed entry points and loosened checks. Projects with only 1 reviewer (blog) have only reviewer 1.
  • Reading earlier steps' history: fix and reflect can use /sandbox/bin/myorch-steps to read, in parts, the manifests and logs of this run's earlier steps (for example why develop did something). The reviewer and verify prompts do not mention it: they must judge independently first. Earlier steps' records (.myorch/, other steps' .claude/) are read-only for every step.
  • Rule markers: rules like "look in the repository", "judge independently first" and "at most 5 Nits" above were added because the model made those mistakes before. They are marked in the flow file with [[rule:<rule>/<location>]], and the reason for each is recorded in rules/registry.yaml. At expansion the marker is removed and the text stays. Only a replay with --set flows.ablate=<rule> removes the whole rule, to evaluate whether the rule is still needed.
  • verify: merges duplicates, opens the code for each finding to confirm it, also confirms findings only one reviewer reported, and deletes those that do not hold. Deletes pure style comments and keeps at most 5 Nits. Each failed check counts as one Important; environment failures do not. Findings from the previous round are marked fixed, open or rebutted. blocking is the number of unresolved Important findings; the loop ends when it is 0.
  • fix: fixes only Important findings, changes all places of one problem together, and leaves Nits alone. When it thinks a finding does not hold, or the fix needs a human decision, it does not change the code and writes it in rebuttal.md instead (those needing a human decision start with "Needs a human decision:" (需要人决定：)); the next round's verify judges it. When the cause is in the project pack, it proposes a project pack change; see the next section. After fixing it runs the checks, appends "Round N fix" (第 N 轮修复) to the end of the implementation record, and commits once.
  • Running out of rounds: with on_exhausted: ask (the default), reflect reads all rounds and judges whether it is an isolated problem, a wrong direction, something needing a human decision, or reviewers being wrong. It gives a proposal and then asks you: run one more round, accept the current result, or stop. With accept (blog) the flow goes straight on. The last round's fixes were never reviewed, and risk-rules lists those commits.
  • The approver requests changes: the comments are written into the next round's approver.json. Each one counts as Important, and verify will not delete them.

Project pack changes (pack-choose, pack-apply)

Sometimes a blocking problem lies in the project pack, for example a mistake in checks.sh. The project pack is read-only in the sandbox (project/), so fix cannot change it. In that case:

  1. fix does not change project/ and does not write a rebuttal for it. It copies project/ to /tmp, changes the copy, runs the relevant checks once with the copy, and writes the proposals to docs/review/round-N/pack/proposals.json (for machines) and proposals.md (for people, including the verification result).
  2. pack-choose lists the proposals and asks which ones you adopt.
  3. pack-apply writes the adopted changes back to myorch-knowledge on the host, commits only those files, and syncs the project snapshot again. The original text of each change must appear exactly once in the file; otherwise nothing is written and the step fails.
  4. The next round of this run mounts the new snapshot and checks with the new project pack. Other runs are not affected. When the write-back happened in the last round, the reflect step proposes one more round.

Only files under guide/, checks.sh, checks.env and setup.sh can be changed (EDITABLE["fix"] in project.py). risk-rules.yaml and security.md cannot: a run must not change how its own changes are approved. To change other files, fix writes "Needs a human decision:" (需要人决定：).

Task info and takeaway

Only when the project sets flows.development.takeaway: true (currently only mdm): putting a myorch/ directory in the repository needs the project's consent. After the review loop and before the risk verdict, four steps commit this run's task info and lessons to the repository.

  • Committed on the branch: takeaway-commit copies task.md and takeaway.md to repo/myorch/<date>-<run ID>/ (the date is the day the run started), commits only this directory, with the fixed commit message Add myorch task and takeaway for <run ID>. When the content has not changed, it does not commit again. It is visible at approval, is in the PR after the push, and reaches the base branch after merging; learn reads it from there.
  • Not blocking: all four steps have on_failed: skip. A failure records a failure event, counts as skipped, and the flow goes on. Each step runs only when the previous one produced output, so stale or half-written files are never committed (takeaway-trail empties both files first).
  • trail: each step's status, summary, failure reason and retry count; questions and answers; each review round's blocking count and check results; branch, inputs, myorch commit, project pack version. Lines that look like secrets are deleted before writing.
  • What takeaway writes: task.md holds only facts (ticket, run, inputs, requirements summary, questions and answers, each review round and its checks, the result). takeaway.md holds the problems met, root causes, how they were solved, what knowledge was missing, and proposals for the flow or platform. Each item is tagged with a category (project knowledge, flow, platform, environment) and gives evidence. "What knowledge was missing" holds only project knowledge that would help with a different requirement too, not the answer to this ticket. The two files together are at most 200 lines. The agent has no knowledge sources attached and is read-only.
  • Reading the history: besides trail.json, takeaway can use /sandbox/bin/myorch-steps to read each step's logs in parts, to find where things first went wrong.
  • No secrets: the two files go into the company repository. takeaway-redact deletes lines that look like secrets by knowledge.SECRET_RULES (the same rules as the knowledge source scan). When both files end up empty it fails, so the commit does not run.
  • How risk-rules sees this commit: it comes after the last review round, but it does not count as a "commit that was not reviewed": a commit with a single parent that changes only .md files under myorch/ is not counted. Merge commits are always counted. risk-rules takes head_sha after this commit, so what you approve and what is pushed is the commit with these two files.
  • When it is not written: replays (at) do not write it; otherwise the eval case's answer would get into knowledge. It is also not written when develop decides no change is needed. A run that fails before approval cannot be pushed, so its lessons are not in the repository.

Risk and approval

Risk is decided by the change, not by the author. Two classifiers back each other up: rules may miss semantic risk, the model may miss path-based risk, and the stricter of the two wins.

risk-rules (deterministic script):

  • The rules come from the project pack's risk-rules.yaml (the template's rules plus the project's own). Of the rules that match, the strictest applies. Rules can match by path, by text in new files, or by a regex on changed lines. When no rule matches, default applies.
  • At least 1 approver in any of these cases: the last review round still has unresolved Important findings; the last round's checks failed; there are new commits after the last review round (for example after accepting when the loop ran out of rounds, so nobody looked at the last round's fixes). The takeaway commit does not count; see the previous section.
  • Outputs approvers (the number the rules require) and available (the number of approvers registered for the project).

classify-risk (agent, read-only): reads the actual diff, the requirements document, the assumptions in the implementation record, the last review round and checks, and the commits that were not reviewed, and decides 0, 1 or 2 approvers. Any one of these means 2: changes to interfaces or data, changes to build or deployment, anything security-related, hard to undo, affects downstream. It writes docs/risk.md: the verdict, the impact, unresolved problems, and 3 to 5 places the approvers should check. The project's prompts/risk.md is appended to the end of the prompt (myorch uses it to require that the impact be written in terms of the platform's boundaries, unfinished runs, and deployment).

Number of approvers for human-review:

min(approvers registered for the project, max(risk-rules count, min(classify-risk count, 2)))
  • All three projects currently register only one approver, so the number is at most 1.
  • mdm: the core-ng template's default is 1. Database migrations, interface modules, build and dependencies, CI and deployment, environment config, entity field annotations and destructive SQL need 2. mdm's protos submodule needs 2 and spec documents need 1. So every run needs exactly 1.
  • blog: default: 1; every run needs 1.
  • myorch: default: 0; the platform's boundaries (code for sandbox, credentials, profiles, deployment, scheduling and approval) need 2. When both judgments give 0 (for example only docs changed), approval passes automatically and deliver pushes the branch right away. Only the branch is pushed; merging and deployment are done by a person.
  • The person who started the run must be one of the approvers (require_initiator). An agent's approval does not count.
  • Approval is bound to a commit: head_sha is recorded when approval opens, and deliver checks it before pushing.
  • Request changes: back to review-fix, at most 2 more rounds. Then takeaway, the risk verdict and approval run again from the start.
  • After 24 hours with no action, one reminder is sent. After 7 days with no action, the step fails ("approval timed out" (审批超时)) and nothing is pushed.
  • If any approver rejects, the run ends.

Delivery

Defined in lib/deliver.yaml.

  • It refuses to push when the current branch is the base branch. It refuses to push when HEAD is not the approved commit; the run must be redone and approved again.
  • Pushes the branch (normal push, no force push). Does not call the GitHub API and does not open a PR.
  • Writes docs/delivery.md: title and ticket, what changed (taken from "Changes" (改动) in the implementation record), how it was verified (check results, acceptance criteria table), number of review rounds and unresolved problems, commits that were not reviewed, the risk verdict and the places to check, how to undo.
  • outputs.delivery carries the branch, base, commit, title, ticket, the delivery note and the repository's PR template. The run_finished event carries it, and the console and Slack use it to tell you which branch was pushed. You open the PR.

Continue (from_run)

The general procedure is in Continue on the same branch. In this flow:

  • checkout-branch mounts the previous run's workspace read-only and starts from its last commit. If someone added commits to the remote branch of the same name, it starts from the latest remote commit. If the two have diverged, it stops and a person must sort it out first.
  • Files copied to docs/previous/: requirements.md, design.md, implementation.md, risk.md, delivery.md, external-request.md (the previous original request), the last review round's review-summary.md, and RUN with the previous run ID. Earlier runs are in earlier/. conversation.md is written by the host: what people said to the previous run.
  • develop's requirements document states the full requirement, with a separate paragraph "This change" (这次的修改) under "Goal" (目标). The previous acceptance criteria still hold unless this request changes them. The design is changed on top of the previous one. The code is changed on top of the existing commits, not redone. Human decisions in conversation.md take precedence over assumptions in the previous documents.
  • checkout-branch outputs since (the commit at the start of this run). Round 1 of the review loop looks only at commits after since; checks still run on the files the whole branch changed against base. The risk verdict looks at the whole branch.
  • It pushes to the same branch, so a PR that is already open updates automatically. If no ticket number or incident is given, the previous ones are reused.
  • Cannot be combined with at.

Replay (for evals)

Used to redo an already merged ticket on the code as it was then, and compare with the merged PR. The form shows at, ticket_as_of and ticket_comments only for projects with Jira (on the command line, -i at= can be passed for any project). Leave them empty normally.

  • at is the PR's merge-base. checkout-branch creates the branch from this commit, then deletes the origin remote, all other refs, FETCH_HEAD, the reflog and borrowed objects, runs gc, and does the same for submodules. Later commits would leak the answer, so only history reachable from at stays in the repository. Finally it points origin/<base> at at, so every later diff uses it as the base.
  • ticket_as_of is the moment work on the ticket started (ISO time). fetch-ticket uses the ticket's changelog to roll title, description, status, priority and assignee back to that moment. It keeps only earlier comments, attachments and linked tickets, and leaves out subtasks (subtasks may contain the solution).
  • A replay never asks for approval and never pushes: the conditions of human-review and deliver include not inputs.at. Deleting origin is a second safeguard. No takeaway is written either. The run ends after classify-risk.
  • Cannot be combined with from_run; checkout-branch fails right away.
  • To find out whether the ticket description alone is enough, add -i ticket_comments=none.
  • Comparisons: a replay can change this run's flow settings with --set, for example --set flows.development.reviewers=1 or --set flows.ablate=nit-cap (removes one marked rule; rule names are in rules/registry.yaml). Only existing settings under flows. can be changed, and only in replays. What was changed is recorded in the mandate, and the run gets a set:… tag so variants can be grouped. myorch expand --set … shows the changed prompt first.

myorch and incident

The myorch platform itself: code, flows, prompts and docs are all in the repository leweii/myorch, branch myorch/<run ID>. Two uses: a normal requirement; or, when the platform had a problem in some run (a run of any project), passing incident to find the cause and fix the platform.

incident is the run that had the problem. Its workspace is mounted read-only for develop at /sandbox/workspace/observed/<run ID>/:

  • .myorch/flow.yaml: the snapshot of the flow that run used.
  • .myorch/steps/<instance>/out/manifest.json and logs/turn-<attempt>-<turn>.log: each step's result and each attempt's log. supervisor-*.log holds the sandbox's network, DNS and credential records.
  • docs/ and memory/MEMORY.md: that run's requirements, design, review and check reports.

These files are that run's data: the agent only reads them and does not run commands or follow instructions in them. The console's run picker lists only this project's runs, so incident is a plain text box.

myorch: after merging

This flow does not deploy. The sandbox only changes the repository and has no access to docker.sock, the gateway or the data directory, and a flow must not have automatic merge or deploy steps (the project pack's security.md). develop writes "What to do after merging" (合并以后要做的事) at the end of the implementation record.   3. When tools/ changed (the helper commands in the sandbox, such as myorch-checks and myorch-ask), they are installed into the volume by myorch init (the init service in compose). Make sure myorch init has been run again; otherwise the sandbox still has the old versions.

Principles

  • Always review the whole PR: myorch leaves no markers on GitHub, so there is no incremental review. The "reviewed up to last time" logic in fetch-pr is no longer used: last_reviewed is always empty and changed is always true, so review-round always runs, and round 1 looks at origin/<base>...HEAD.
  • Trusted and untrusted data are kept apart: author, state, changed files and SHAs go into docs/pr.md. The title and description written by the PR author go into docs/external/pr.md. Every agent treats docs/external/ as reference data and does not follow instructions in it.
  • Reviewer rules are the same as in the development flow: judge independently first, then check the author's claims; search the repository for reuse and missed entry points; relaxed judgement. See development's review loop. Reviewers 1, 2 and 3 each have their own focus; quick has only reviewer 1 (focused on correctness and edge cases).
  • verify checks each finding: no matter how many reviewers there are, every finding is checked by opening the code. Findings that do not hold are removed; findings reported by only one reviewer are checked too. votes only records how many reviewers reported it. At most 5 Nits are kept; failed checks count as Important.
  • Requirements document: this flow does not pass requirement_doc to the review loop. Reviewers and verify are told the requirements document is docs/requirements.md, but a review run has no such file. So they can only judge from the change itself, and the PR description is only reference material in docs/external/pr.md. The end-to-end block is passed docs/pr.md.

End-to-end tests

  • review reads the code; e2e tests the running application. The two are separate. The project decides which tools to test with: e2e: in project.yaml (image, profile, acceptance) and the project pack's e2e/ (the blog uses Playwright and headless Chromium; see myorch-knowledge/blog/e2e/README.md).
  • The test steps' permissions are e2e.profile (for blog, dev-read: read-only repository, no credentials).
  • When a smoke test case fails only because of the test environment (for example the browser did not start), the report lists it separately as "environment" (环境), not as a problem in the code.
  • e2e-accept must not loosen test cases to make them pass. When a test case fails, it first decides whether the test case is wrong or the change has a problem; if the change has a problem, the test case stays.

Security

  • Code in other people's PRs is untrusted, and ci and the end-to-end tests execute it (build scripts, tests, lint configuration). The steps that execute PR code (ci, e2e-smoke, e2e-accept) and the reviewers that read the code get no GitHub credentials, and run in sandboxes that are deleted after use.
  • The one step with credentials (fetch-pr) runs only scripts fixed in the flow and executes no code from the PR. It only reads: fetches code, reads the PR.
  • The remaining risk is prompt injection: PR content may lead reviewers to misleading conclusions. Conclusions are shown only on the local machine and not posted to GitHub.

audit: what it looks for

  • Correctness (logic errors, missed edge cases, unhandled errors, mismatches with docs or comments), security (injection, leaked secrets, unsafe defaults, missing permission checks), errors users see (broken links, wrong data or display).
  • Each auditor has its own focus: auditor 1 looks more at correctness and edge cases, auditor 2 at security and error handling, auditor 3 at whether docs and data agree.
  • Not reported: code style, naming, things that could be written better but are not wrong, missing tests; known issues; code outside this batch of files (used only to understand context).
  • There are only two severities: Important (wrong behaviour, wrong data, security problems; worth having someone fix) and Nit (really a problem, but with small impact). Findings it is not sure about are not reported.
  • When there is a guide/review-guide.md, it follows its standards.

verify: verification

  • Each finding is checked by opening the code; findings that do not hold are removed.
  • The same issue reported by several auditors is merged into one, and votes is the number of auditors who reported it. Findings reported by only one auditor are kept if they hold.
  • Findings that are the same issue as one in known.json are removed.
  • The daily report: with no new issues, it has only the sentence "No new issues found in this batch of files." (这批文件没有发现新问题。), followed by the directories that were looked at. With new issues, the first sentence gives the number of Important and Nit findings, then lists each one by severity with its location, the problem, the consequence and a suggested fix. collect: what happened to the findings

Findings already marked fixed do not count. Each of the others is checked in the order below, and the first that holds wins:

Outcome Meaning
fixed In a later round, a finding in the same file is marked fixed
rebutted The first 12 characters of the title appear in some round's rebuttal.md
merged_unchanged / closed / open Review runs only: the reviewed PR was merged, was closed, is still open
not_required Nit or Pre-existing; it never blocked
unknown None of the above

myorch no longer posts comments on PRs, so there is no "someone replied to the comment" outcome. Outcomes come only from the runs' own records and the PR state.

collect: takeaways in the repository

  • When the project sets flows.development.takeaway (currently only mdm), development commits task.md and takeaway.md with each change to myorch/<date>-<run_id>/. They reach the base branch only after the PR is merged, so only merged ones can be read. Other project repositories have no such directory, and this kind of signal is empty.
  • When the workspace has no repository, collect makes a shallow clone without checking out files and reads them one by one with git show.
  • Learned ones are skipped, and reading starts from the oldest. At most 30 entries and 300 KB per run (the first one is always read); the rest wait for the next run. The digest says how many are left.
  • An entry whose takeaway.md cannot be read (network problem, empty file) is not read and not marked learned; the next run tries again. After 3 unreadable entries in a row it stops. Directories whose name is not <date>-<run_id> are skipped.
  • When the repository cannot be read, it records only a fixed sentence and the git exit code, without the command line or git's output. learn carries on.
  • Which ones were learned is recorded only on the local machine in myorch-data/learn/<project>/takeaways.json (takeaways.py). Nothing is written to the company repository or to myorch-knowledge.

analyze: which kinds of knowledge it looks for

At most 8 proposals. With too little evidence it proposes fewer or none. It does not repeat what the knowledge and the repository's own docs already say. The wording is short and follows the style of the existing files.

Type What it looks for Where it writes
record-decision Decisions a person made while answering during requirements analysis or design that apply to all similar questions later guide/decisions.md (created when missing): the situation, what to do, why, the source. Later similar questions follow it without asking a person
fill-gap Causes of rework: continuations, postmortem conclusions, implementations that deviated from the requirements or design, assumptions that had to be made Guides for development and design. The question is "what could the knowledge have said in advance so that the first attempt was right"
add-rule The same kind of problem recurring (in at least 2 runs, or in 1 with high impact) Rules to avoid during implementation, or review-guide.md
relax-rule Comments that were rebutted repeatedly, or merged without changes Relax review-guide.md
add-check Recurring problems a script can detect, or CI checks that fail repeatedly checks.sh or checks.env. Only deterministic checks; checks that may give false positives only warn. When it is not sure it can write the check correctly, it goes into follow-ups.md

Two more files are never applied: follow-ups.md holds proposals for changing the project repository itself (lint, CI, tests), which need a separate development run; flow-proposals.md holds proposals for myorch flows (step order, when to ask questions, steps that always fail or are not needed).

Takeaways are treated as signals and checked like other evidence: only project knowledge that generalises to later work is adopted, not what holds only for one ticket. Evidence is written as <run_id>: takeaway. Proposals about flows, the platform or the environment go into flow-proposals.md.

Each proposal's change is written as an exact replacement (edits: old copied verbatim from the current file and occurring exactly once in it) or an append (append). No diffs, because diffs written by agents often have wrong line numbers.

Not leaking the answers

  • The answer key stays out of the workspace: myorch eval run writes only the case fields that may be seen into docs/eval/case.json: origin, source run, flow, repository, base and head commits, requirements document. The findings a person confirmed stay on the local machine in myorch-data/evals/cases/.
  • Later commits are not kept: the source run's later fix commits would tell the reviewer where the problems are. So the repository keeps only the history reachable from head. Branches, remote refs and the reflog are deleted.
  • Nothing outside is writable: after origin is deleted, no step in the replay can push.
  • The reviewer also does not see the source run's technical design, implementation notes or the original ticket text. The workspace contains only the requirements document and the change. So the eval's review has fewer inputs than a review in the real development flow.

How scoring works

Scoring happens on the local machine, not in the flow:

  • Only Important and Nit are compared, on both sides.
  • Caught: a replay finding is in the same file as a marked finding and the line numbers differ by at most 10 (a match on any one location counts).
  • Missed: marked findings that were not caught.
  • Extra: findings the replay reported that matched no marked finding. They may be false positives, or real issues nobody flagged at the time. The number of Important ones among them is listed separately.
  • report first lists each run (depth, case, caught/expected, extra), then sums up per depth: cases, expected, caught, missed, recall (caught ÷ expected), extra, extra Important. Postmortem replays are split into "depth·before" (强度·before) and "depth·after" (强度·after). Runs that have not finished are not counted, and a note at the end says how many are still running.
